Herdr app mod · blueprint

Suggestion box

Agents may not fix unrelated code mid-ticket, so what they spot gets lost. With this, an agent drops a note in the project's box and carries on. Your own Claude checks each note against the code before you file it as a GitHub issue on the project's board, in one standard layout. A note an agent claims as solved waits until you have seen the proof. One more click opens an issue as a ticket tab where Claude fixes it.

Part A

The suggest command

The text comes on stdin, in a quoted heredoc, one key: value per field. The shell runs nothing inside a quoted heredoc, so backticks, quotes and $ in code are safe. A line starting with two spaces continues the field above. For a quick note by hand, the same fields work as flags.

# drop a note
suggest <<'EOF'
title: formatDate throws on a null date
at: src/invoices.ts:42
problem: Invoices without a due date crash the PDF export.
evidence: A fixture with `dueDate: null` made `exportPdf` throw
  `TypeError: Cannot read properties of null (reading 'getTime')`.
current: `formatDate(null)` throws, so the export answers with a 500.
desired: `formatDate(null)` returns a dash and the export works.
EOF

# the project's notes that are open or to verify
suggest list

# the agent's own task fixed a note after all
suggest solved 7 <<'EOF'
how: formatDate returns a dash for null now
proof: invoices.test.ts: formats a missing due date as a dash
EOF

  • The same note means the same project, the same title (ignoring case, extra spaces and a final full stop) and the same file, in any state the box keeps: open, to verify, solved, filed or binned. A repeat counts and keeps the state, so a note you binned or filed never comes back as a new one. The one exception: a note confirmed solved reopens, because seeing it again means the problem is back.
  • Note numbers count up per project and are never reused: a drop claims its number by creating numbers/<n> with exclusive create, and a tombstone keeps each number after old notes are deleted.
  • Many agents at once: the command never rewrites a note. A drop creates a new file; a repeat or a claim adds an event file beside it, also with exclusive create. Only the box folds events in and rewrites notes, with compare-and-swap. So drops never clash, no agent write can undo a filing, and there is no lock to go stale.
  • suggest list shows notes that are open, to verify or filed (with their issue), so an agent can also claim a filed note.
  • With a line, the command also keeps the five lines around it, so the box can find them again after the code moves.
Part B

How agents know about the box

Two entries in ~/.claude/settings.json, both added by install.sh with a backup first, and taken out exactly by uninstall.sh. The instructions are tried in your safepath project before they go on your machine.

1 · the instructions, from a session-start hook

At the start of a session, after /clear and after a compaction, the hook runs suggest session-start. It prints this text only in a git repo where collecting is on; otherwise nothing, and the session never hears of the box, as before the mod. Subagents most likely don't get it, which keeps review agents out; PR 1 checks this.

## Suggestion box

When you notice a real problem outside your
current task (a bug, a risky pattern, a missing
test, dead code, wrong docs), do not fix it and
do not let it pull you off course. Drop a note
and carry on. Run `suggest list` first: dropping
a note that is there already only counts.

```sh
suggest <<'EOF'
title: <what is wrong, one line>
at: <file>:<line>
problem: <what is wrong, who or what it hurts>
evidence: <what you actually saw>
current: <what the code does now; quote it>
desired: <what should happen, from the code's
  own types, tests, docs or the ticket>
EOF
```

All four sections are required and become the
issue, so write only what you checked, no
guesses. Not sure what should happen? Write
"Unsure: <the question>" as desired. Write in
plain English without any chat style, and leave
out secrets, tokens, customer data and personal
paths: teammates read it, and the repo may be
public. If `suggest` says the box is off, drop no
more notes in this task and name your findings in
your final report instead.

Only drop what a teammate would want an issue
for: no style nits, nothing your own task should
fix, at most a few per task. Only in your main
session on a task: as a subagent, a reviewer or
in a read-only task, report findings to whoever
asked you instead. Never file an issue yourself;
if `suggest` is missing or fails, name the
finding in your report instead.

Every drop answers with the note's number. If
your own task ends up fixing a note after all,
claim it, naming a real test or check; the user
verifies it before the note is closed:

```sh
suggest solved <number> <<'EOF'
how: <what fixed it, one line>
proof: <the test or check that shows it>
EOF
```

In your final report, list the notes you dropped
and the ones you claimed solved.
2 · the permission rule

Bash(suggest:*) goes into permissions.allow in ~/.claude/settings.json, so a drop never stops an agent for a prompt.

That is safe because the command only drops, lists and claims notes solved, all in local files. It cannot file issues or confirm anything; only you can, in the box.

How it fits the team flow

ship-issue already puts out-of-scope things under "Risks and open questions" in its plan. The note keeps them after the ticket is done. No team skill changes.

Ruled out

A skill (may not trigger mid-task), an MCP server (more moving parts for one command), a hook (hooks see tool calls, not what an agent notices).

Part C · when the agent fixes it after all

Solved along the way, and proven

Sometimes the agent's own task ends up fixing what it noted. Then the note must not linger, or become an issue for work that is already done. But "an agent said so" is not proof. So a note claimed solved does not leave the box until you have seen the proof and confirmed it.

Three ways a note gets claimed, one place it lands: To verify

  1. The agent says soIt runs suggest solved 7 with how and proof, naming a real test or check.
  2. The box sees the code movePlain git maps the note's lines forward through git diff -U0 -M, anchored on its snippet, also through moves, renames and rebases. Changed on its branch or on main: a changed on … chip and Mark solved. No Claude.
  3. The check spots itWhen you open File issue and the problem is gone, the banner offers Mark solved, so no issue is filed for done work.

Part C · the rules

Note states: what you can do with each

Every note is in exactly one state, and each state allows a fixed set of actions. The box shows only the buttons of the state and refuses any other action, also one that races in, like an agent's claim while you edit. A note claimed or confirmed solved can never be filed.

Moves between states

  • Open → Claimed: an agent runs suggest solved, you press Mark solved, or the check's banner says the problem is gone and you press Mark solved there.
  • Claimed → Solved: Confirm solved. Claimed → back where it was (open, or filed): Not solved.
  • Solved → Open: Reopen, or an agent drops the same note again, because the problem is back. The watch finding that the fix never landed sends it back to Claimed.
  • Open → Filed: Create issue. Open → Binned: Bin. Binned → Open: Restore.

The two races

  • The check finds the problem gone: the banner shows and Create issue is off. You choose Mark solved, Bin, or It is not solved when you disagree with the check, which turns Create issue back on and keeps your reason in the note.
  • An agent claims the note while you edit it: the editor closes with An agent claimed this solved on feat/…; see To verify, your draft is kept, and Create issue cannot go through.
  • Create issue is never off without a reason: one line under the buttons says why: waiting for the check, the check says this is solved, a section to fill in, or a sensitive item in a public repo.

Part D · the check

Filled in automatically, but correct

The agent wrote the sections while it was busy with another ticket, and code moves on. So the moment you open File issue, the box asks your own Claude to check them against the code.

How it runs

  • claude -p with the flags parrot already uses: --model sonnet, its own --system-prompt, --json-schema for the answer, --setting-sources "", --strict-mcp-config, --no-session-persistence.
  • It reads snapshots, never the working tree, which can be stale, dirty or on another branch: the box fetches, exports origin/<default> and the note's branch into two temporary folders (git archive) and runs Claude there. A ticket worktree's uncommitted diff is passed in too; the folders are removed afterwards.
  • Its only tools are Read, Grep and Glob. No git and no shell: git grep -O can start a program and --output can write a file, and the check reads text that agents wrote.
  • Usually 10 to 30 seconds. After 90 seconds or on a failure, the labels say Not checked, Create issue works again, and Check again retries.
  • The result is kept in the note and reused until the diff of the note's file changes. A field you edit yourself loses its label.

Part D · where it goes

Repo, label and board

The box reads the project's .ai-tooling/config.yml (or .claude/project.yml in a repo the team sync has not moved yet) from the freshly fetched origin/<default>, as the launcher does: the same file the team's skills read for ship-issue and create-pr. A missing status.todo means no column is set; a label the repo lacks is named in the target line and left off.

  project: { owner: acme, number: 41 }

  status:
    field: Status              # the board's column field
    todo: Backlog              # the column a new issue goes to
labels:
  needs-triage: triage         # the label it gets

Create issue runs three steps

  1. gh issue create in the repo, with the title, the standard text and the label.

What one click does

  1. Picks the branch the way parallel-tickets names them: fix, docs or chore, and three to five words from the title, no number. issues branch checks it: taken gets -2, ci: or invalid gets another name.
  2. Runs the launcher in a background terminal of herdr-core, from the project's main checkout, with --space.
  3. The launcher fetches origin, bases the branch on the fresh default branch, opens the tab through hagent and sends the ticket prompt, which starts with /ship-issue 812.
  4. The note shows Fixing in fix/… ↗; a click jumps to that tab.
issues launch --space <space> --ticket 812 --branch fix/formatdate-throws-null-date

--space is new, and it has to reach hagent too: today the launcher reads the space only from the app terminal's label, which a background terminal lacks, and it unsets the HERDR_ACTIVE_* values hagent would read. So --space sets HAGENT_HOST=app and hands the space to hagent. Where the change goes is the open question below. The button shows only when the launcher and its hagent are there, the launcher knows --space, and the config has a GitHub tracker on the origin repo, since ship-issue stops on anything else. From there it is your normal ticket flow: ship-issue verifies the problem, posts its plan and waits for your go, and stops after the review without a push or a PR.

  • status: open, filed, binned or solved (confirmed). A note is in To verify while it has a solved claim without confirmed; its status stays what it was, so Not solved puts it back exactly there.
  • ticket: from parallel-tickets' record of the branch, else a <type>/<number>-… branch name, else null. Any other number in a branch name proves nothing (chore/bump-node-20).
  • snippet: the five lines around the line at the drop, used to find them again after the code moves.

  • Filed, solved and binned notes are cut down to a tombstone after 30 days: number, normalised title, file, final state and issue. Tombstones stay, so a binned note never comes back and a number is never reused.
Setup

Install and uninstall

./install.sh can run again any time, like parrot's. Every file it changes is kept beside it first. It runs on your machine only on your ok, because it changes what every agent does.

  1. Links the mod to ~/.config/herdr-app/mods/suggestion-box.
  2. Adds to your layout the button at the end of the tab bar, after Quarterdeck's, and the panel as a hidden 400 px column on the right next to Quarterdeck's and Chartroom's (a copy for Herdr's own layouts, as parrot does).
  3. Binds cmd-alt-s to layout.toggle:suggestion-box in keys.json when it is free.
  4. Links bin/suggest to ~/.local/bin/suggest.
  5. Adds the SessionStart hook (suggest session-start) to ~/.claude/settings.json.
  6. Adds Bash(suggest:*) to ~/.claude/settings.json.
  7. Runs herdr-app check on the mod.

./uninstall.sh undoes each step and keeps your notes and settings, unless you pass --purge.

Build order

Seven PRs, one version each

Each is reviewed and merged before the next starts, built the way you work.

How each PR is built

  • The folder is not a git repo yet: on your go for PR 1 it becomes one, with this plan and the sketch as the first commit on main.
  • Built in its own worktree, opened as a ticket tab through hagent. The linked checkout that every agent's suggest and the live mod run from stays on main, so half-done code never reaches them.
  • Its plan is posted first in your format, Single PR: [title] — [files] — ~[lines], and waits for your "go".
  • The branch is made before the first edit; nothing is edited on main.
  • Several logical conventional commits; no Claude in them, no Co-Authored-By.
  • Before the report: bun test, herdr-app check and a local review whose real findings are fixed.
  • Then a report, and stop. No push and no PR without your ok for that one; updating a branch is a rebase onto origin/main, and its force-push needs its own ok.
  • Merges, tags (vX.Y.Z, the number only in package.json) and releases on your ok, as with parrot; CHANGELOG in Keep a Changelog. After a merge ./install.sh runs again.

  • PR 2 starts with a short spike, as parrot's did, to prove what the mod API does not promise: writing and watching ~/.suggestion-box from the mod, exec with a 90-second timeout, render running again when the layout changes, and the icon (one of Herdr's own, since icons through the install link do not draw).
